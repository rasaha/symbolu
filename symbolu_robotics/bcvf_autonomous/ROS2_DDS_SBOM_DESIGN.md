# ROS 2 / DDS / SBOM integration contracts — design

The §9 row #2 industry-features-roadmap pick. Every Tier 1 / OEM /
robotics customer's first three questions look identical:

1. *Does it speak ROS 2?*
2. *What's the DDS QoS profile?*
3. *Where's the SBOM?*

This doc specifies the answers we ship as integration contracts.
It composes with the existing `bcvf_ros2/` framework-agnostic
scaffold (`BCVFTrustBridge`, `PredictedTrajectories`,
`TrustDistribution` dataclasses, lazy-rclpy shim, 13 tests)
rather than rebuilding it. The new pieces are: typed `.msg`
schemas, a `BCVFNode` behavioural class with rate-limiting +
deadline-awareness, the documented DDS QoS profile, and a
CycloneDX SBOM. All ship in `PROVISIONAL_API` per the §11
maturation discipline.

## §1 Why this exists

A buyer's first technical filter for a perception / planning
arbitration component is: *"does it integrate with our existing
robotics stack at all?"* In the autonomy / robotics market the
answer to that question is structural: ROS 2 + DDS for the
on-vehicle bus, CycloneDX SBOMs for the procurement gate. A
component that doesn't speak those protocols isn't on the
shortlist.

Today the runtime ships a working framework-agnostic scaffold
(`bcvf_ros2/`) with a tested pure-Python bridge. What's missing
is the contract layer — the typed message schemas, the QoS
profile, the SBOM — that lets a deployment partner answer the
three questions on day one of a diligence engagement, instead of
*"we'll figure that out during integration."*

This is **Item #2 on the §9 deal-unlock ranking** (after the
functional-safety state machine, which shipped in v0.7.x).
Estimated effort 1–2 weeks; lands as design-doc + provisional
implementation + tests pair, same maturation pattern as the
state machine.

## §2 The three first-call questions, answered

| Question | Answer this doc ships |
|---|---|
| *Does it speak ROS 2?* | Yes — `bcvf_ros2/` package with typed `.msg` schemas (`PredictorTrajectory.msg`, `ConsensusOutput.msg`), a `BCVFNode` that subscribes to per-predictor trajectory topics and publishes consensus + per-predictor attribution, and a lazy-rclpy shim so the test suite runs without ROS 2 installed. |
| *What's the DDS QoS profile?* | The `RELIABLE / VOLATILE / 10ms deadline / 100ms liveliness lease` quad. Documented in `bcvf_ros2/qos.py` as the `DDS_QOS_PROFILE` constant + a typed dataclass an integrator can copy into their config. Rationale documented per knob. |

## §3 ROS 2 message contract

### §3.1 PredictorTrajectory.msg

One message per predictor per planning step. Topic per
predictor: `/bcvf/predictor/<name>/trajectory`.

```
# bcvf_ros2/msg/PredictorTrajectory.msg
std_msgs/Header header        # stamp + frame_id
string predictor_name         # M1 / M2 / M3 / M4 / etc.
uint32 horizon                # H
uint32 num_rollouts           # K (1 for single-trajectory predictors)
geometry_msgs/Pose2D[] poses  # K * H, row-major (rollout, step)
```

### §3.2 ConsensusOutput.msg

One message per planning step, published by `BCVFNode` after
running the trust-shaping bridge over the latest set of
`PredictorTrajectory` messages.

```
# bcvf_ros2/msg/ConsensusOutput.msg
std_msgs/Header header                # stamp + frame_id
string[] predictor_names              # length M, ordered
float64[] trust_weights               # length K * M, row-major (rollout, predictor)
uint32 num_rollouts                   # K
float64[] bcvf_total                  # length K — diagnostic
float64[] ema_mean                    # length M, may be empty if disabled
float64[] ema_std                     # length M, may be empty if disabled
uint32 deadband_active_count          # K-side count
bool[] is_excluded                    # length M, may be empty if exclusion off
string safety_state                   # NORMAL / DEGRADED / FAULT / FAILSAFE
uint8 safety_state_asil_class         # 0 = N/A, 2 = ASIL-B, 4 = ASIL-D
```

The `safety_state` + `safety_state_asil_class` fields are the
new piece — they extend the bridge output with the four-state
posture from `safety_state.SafetyStateMachine` so a downstream
planner can condition on the system-level state without running
its own copy of the state machine.

### §3.3 BCVFNode wiring

Subscribes to one `PredictorTrajectory` topic per registered
predictor (configured at node-init time). Buffers the latest
message per predictor with arrival timestamp. Runs a Timer at
the configured `publish_rate_hz` (default 100 Hz, matching the
10 ms deadline). On each tick:

1. Check that every predictor has a fresh message (arrival
   timestamp within the deadline window). Stale predictors
   surface as a deadline-violation log entry + are emitted with
   `is_excluded=True` in the consensus output.
2. Stack the latest per-predictor trajectories into the
   `(K, M, H, 3)` tensor the bridge consumes.
3. Run the bridge (`BCVFTrustBridge.step`).
4. Run the safety state machine (`SafetyStateMachine.observe`)
   over the trust-result snapshot.
5. Publish a `ConsensusOutput` with both the bridge output and
   the state-machine state.

Rate-limiting and deadline-awareness are properties of the node
behaviour, not of the bridge itself. The framework-agnostic
behaviour class (`BCVFNodeBehaviour`) is testable without rclpy
— pass it a fake clock + fake "publish" callable, drive it
tick-by-tick, assert the published output stream.

## §4 DDS QoS profile

`bcvf_ros2/qos.py` ships the `DDS_QOS_PROFILE` constant: the
`RELIABLE / VOLATILE / 10ms deadline / 100ms liveliness lease`
quad with `KEEP_LAST` history depth 1.

| Knob | Value | Why |
|---|---|---|
| reliability | RELIABLE | Trust-shaping output is a control input — best-effort delivery would silently drop consensus updates the planner depends on. RELIABLE pays the retransmit cost; the alternative is the planner running against a stale weight distribution. |
| durability | VOLATILE | The output is per-tick; a subscriber that joined late should NOT receive cached old consensus messages (which would drive the planner against stale evidence). VOLATILE matches the per-tick semantics. |
| deadline | 10 ms | One planning tick at 100 Hz. A `BCVFNode` that misses the deadline by more than one tick is missing-control-loop, not slow. The QoS-level deadline lets the DDS layer surface the violation as an event a watchdog subscribes to. |
| liveliness lease | 100 ms | One order of magnitude above the deadline — bounds the time before a stalled `BCVFNode` is noticed by every subscriber. Tighter than this trips false-positives on transient OS scheduling jitter. |
| history | KEEP_LAST | Per-tick semantics — older messages are obsolete by the time a new one is published. |
| depth | 1 | Match `KEEP_LAST` — never queue more than the latest message. |

The constant is exposed as a Python frozen dataclass with the
six fields above. A real `rclpy.qos.QoSProfile` is built from
the dataclass at the rclpy boundary (lazy import in the shim, so
the dataclass itself is testable without rclpy).

## §5 Rate-limiting + deadline awareness

The `BCVFNodeBehaviour` class enforces three timing invariants:

1. **Bounded publish rate.** Output `ConsensusOutput` at the
   configured `publish_rate_hz` (100 Hz default), regardless of
   how often inputs arrive. The DDS layer's `RELIABLE` mode
   guarantees delivery, but the consensus computation is
   per-tick — multiple input messages between ticks coalesce
   into a single output.
2. **Per-predictor deadline.** Each predictor's message has a
   wall-clock arrival timestamp. If the time since last message
   for any predictor exceeds `predictor_deadline_ms` (default
   100 ms), the predictor is marked deadline-violated for the
   next tick: it appears in `is_excluded` of the output, and
   the safety state machine sees the exclusion via the same
   path live data would take.
3. **Stale-on-resume protection.** When a previously
   deadline-violated predictor starts publishing again, its
   first fresh message must clear the deadline before the
   predictor returns to good standing — single fresh
   ticks shouldn't bounce the deadline status.

Tests pin all three behaviours against a synthetic clock.

## §6 CycloneDX SBOM

The SBOM is the "where's your dependency manifest with versions
+ licenses" answer the procurement gate asks. CycloneDX 1.5 is
the format the SOTIF / ISO 26262 packages standardised on; it's
also what most OSS scanners (Dependency-Track, OSS Review
Toolkit, OWASP) accept directly.

`safety_case/sbom/generator.py` implements:

```python
def generate_cyclonedx_bom(
    *,
    package_name: str = "symbolu_robotics.bcvf_autonomous",
    package_version: Optional[str] = None,
    components: Optional[Sequence[SBOMComponent]] = None,
) -> Dict[str, Any]:
    ...
```

The generator:

* Reads runtime dependencies via `importlib.metadata` (no
  internet access required — sandbox-friendly).
* For each, resolves the installed `version` and the
  `License` / `License-Expression` metadata.
* Maps to SPDX license identifiers where the package uses the
  standard names (BSD-3-Clause, MIT, Apache-2.0, etc.); falls
  back to a textual `name` field on unknown licenses.
* Emits a deterministic CycloneDX 1.5 JSON document with sorted
  components + frozen serialisation order so the on-disk
  snapshot is byte-stable.
* Writes the JSON to `safety_case/SBOM.cdx.json` (the snapshot
  pinned by tests).

The runtime dependency set is intentionally small —
`numpy >= 1.24` plus stdlib — so the SBOM is auditable by hand.
Optional dependencies (anthropic / openai / fastapi / etc. from
the LLM-side of the package) are out of scope for the autonomy-
runtime SBOM; this manifest covers only the
`symbolu_robotics.bcvf_autonomous` import-graph.

A test pins the on-disk snapshot byte-equal to
`generate_cyclonedx_bom()` output so a dependency add / version
bump that doesn't refresh the snapshot fails CI loudly.

## §7 Composition with existing surfaces

* **`BCVFTrustBridge` (existing).** The bridge is the framework-
  agnostic core. `BCVFNodeBehaviour` is a thin wrapper that adds
  rate-limiting + deadline-awareness + safety-state-machine
  composition; the bridge does the trust-shaping math.
* **`SafetyStateMachine` (post-v0.7.x).** The node behaviour
  feeds each tick's exclusion + BCVF totals into the state
  machine and emits the resulting state in `ConsensusOutput`.
  Direct-jump prohibition still enforced — the state machine's
  invariants don't change because it's wired into ROS 2.
* **`StreamingFleetMonitor` + `AlertRule` (existing).** A fleet-
  scale operator can subscribe to every vehicle's
  `ConsensusOutput` topic and feed it into the streaming
  monitor for cross-fleet alerting. The monitor doesn't change.
* **SOTIF / ISO 26262 traceability matrix.** Three new evidence
  artifacts (BCVFNode behaviour, DDS QoS profile, SBOM)
  reference SOTIF clause 5 (functional spec — system boundary)
  and ISO 26262 Part 6 §8 (architectural design). Clause 12.1
  (process-related — release to market) gains the SBOM as the
  configuration-management artifact.
* **`_api.py` PROVISIONAL_API.** New symbols:
  `bcvf_ros2.BCVFNode`, `bcvf_ros2.BCVFNodeBehaviour`,
  `bcvf_ros2.BCVFNodeConfig`, `bcvf_ros2.DDS_QOS_PROFILE`,
  `bcvf_ros2.DDSQoSProfile`, `safety_case.sbom.SBOMComponent`,
  `safety_case.sbom.generate_cyclonedx_bom`,
  `safety_case.sbom.write_cyclonedx_bom`. Count lock bumps
  29 → 37.

## §8 What this is NOT

* **Not a real-time runtime.** The Python implementation runs
  inside a CPython interpreter and is bound by the GIL. Real-
  time deployment requires the C++ port (out of scope; tracked
  separately as §2 RealTimeBudget on the roadmap).
* **Not a replacement for the integrator's stack.** The
  `BCVFNode` is one node among many; it does not replace the
  planner, the perception stack, the localization stack, or the
  vehicle-control bus.
* **Not a full ROS 2 package as installable from rosdistro.**
  Shipping to rosdistro requires colcon build + package.xml
  metadata review + a maintainer release process; the scaffold
  ships the source layout but not the rosdistro entry. That's a
  manual-step ship-when-ready criterion in §9.
* **Not a substitute for the deployment partner's own SBOM.**
  Their full vehicle-stack SBOM enumerates hundreds of
  components; ours covers the autonomy-runtime import graph
  only. Their SBOM aggregates ours alongside everything else.
* **Not a network protocol on top of DDS.** We ship the QoS
  profile rationale; we do not ship a custom DDS plugin or a
  novel transport layer.

## §9 Ship-when-ready criteria for STABLE_API graduation

The ROS 2 / DDS / SBOM surface ships in `PROVISIONAL_API`.
Promotion to `STABLE_API` requires:

1. **One deployment partner runs the `BCVFNode` against a real
   ROS 2 humble (or newer) installation, with their actual
   predictor stack publishing to `/bcvf/predictor/*/trajectory`,
   for one quarter without filing a message-schema change
   request.** The schemas in §3 are explicit; either they fit
   real predictor outputs or they need to bend. Three months of
   live deployment is the empirical filter.
2. **One deployment partner accepts the SBOM into their
   procurement pipeline without an objection.** Procurement
   teams have idiosyncratic SBOM-review checklists; an explicit
   accept-into-pipeline event is the certification floor.
3. **The DDS QoS profile is exercised against a real RTI
   Connext or eProsima FastDDS deployment.** The defaults in §4
   should clear those vendors' compatibility bars; an explicit
   round-trip pub/sub run is the verification gate.
4. **Colcon build of `bcvf_ros2/` produces installable artifacts
   under ROS 2 humble + jazzy + the next LTS.** This is the
   "you can `apt install` this" gate; until it lands, the
   package is "ships as Python source" not "ships via apt".
5. **External auditor confirms the SBOM clears CycloneDX 1.5
   schema validation on a recognised validator (DependencyTrack
   or equivalent).** Automated check; out-of-sandbox manual
   gate.

Until all five land, the symbols stay in `PROVISIONAL_API` and
the API stability policy in `API_STABILITY.md` §2.2 governs
their evolution.

# bcvf_ros2/node.py

@dataclass
class BCVFNodeConfig:
    bridge_config: BCVFTrustBridgeConfig
    publish_rate_hz: float = 100.0
    predictor_deadline_ms: int = 100
    state_machine_config: Optional[SafetyStateMachineConfig] = None

class BCVFNodeBehaviour:
    """Framework-agnostic node behaviour — testable without rclpy."""

    def __init__(self, config: BCVFNodeConfig,

    def safety_state(self) -> SafetyState: ...

    @property
    def deadline_violations(self) -> Tuple[str, ...]: ...
