# Live Pilot Data Handling and Privacy Rules

*Phase 8. Binding constraints for any live shadow pilot. The live shadow pilot must NOT create
a new unauthorized external-model data flow. Where a policy fact is unknown, it is marked
**UNRESOLVED** rather than asserted as a guarantee.*

## Hard rules

- **No credentials in logs.** No raw API keys, tokens, or secrets are ever written to audit
  records, results, manifests, or the repository. Credential *presence* may be recorded; values
  never are.
- **No unrestricted customer prompts in evaluation artifacts.** Shadow records store request
  *metadata* (token counts, feature flags, task class, hashes) — not raw partner prompt content —
  unless an explicit, approved retention policy says otherwise.
- **No new provider receives partner data without explicit approval.** Stage B compares gate
  predictions against outcomes *already generated by normal execution*; it does not send partner
  content to any additional provider for evaluation.
- **Synthetic prompts only for connectivity probes.** Stage A / counterfactual probes use
  synthetic, non-customer content exclusively.
- **Counterfactual probes** are permitted only where policy, consent, privacy, and spend controls
  explicitly allow, and only with synthetic content — never raw partner prompts.

## Redaction and minimization

- Redact before persistence: strip credentials, project IDs, account IDs, and endpoint secrets
  from every record. Store request content as a salted hash or omit it; store only the metadata
  needed for the endpoints in `LIVE_SHADOW_PILOT_PROTOCOL.md`.
- Minimize: persist the smallest fields sufficient to compute the pre-registered metrics.

## Retention, deletion, access

- **Retention period:** UNRESOLVED — must be set by the data owner before Stage B; default to the
  shortest window that supports the analysis, then delete.
- **Deletion process:** a documented, executable purge of shadow records after the retention
  window or on request; deletion must be logged (without re-exposing content).
- **Access controls:** UNRESOLVED — restrict shadow records to the pilot operators; enforce via
  the deployment environment's access controls before Stage B.

## Audit-log fields (allowed)

decision id; request fingerprint (hash); task class; token counts; feature flags; predicted
state; reason codes; evidence sources + ages + timestamps; policy version; registry version;
observed outcome label; latency; **estimated** cost; provider + model id; region. **Not** allowed:
raw prompt/response content, credentials, unredacted account/project identifiers.

## Provider response content

Treated as sensitive: store only what a metric needs (schema-valid boolean, outcome label,
token counts). Do not persist raw response text in shadow artifacts unless an approved policy
permits it.

## Project IDs, account IDs, endpoint metadata

Redacted to a stable non-reversible token (e.g. last 4 chars or a salted hash). Full identifiers
never enter artifacts or logs.

## Permitted vs prohibited counterfactual execution

- **Permitted:** synthetic-content probes to approved providers within spend/quota caps, for
  connectivity/latency/quota/billing calibration.
- **Prohibited:** sending real partner content to any provider for evaluation; probing
  non-approved providers; any probe that would breach residency or enterprise policy.

## Unresolved policy facts

Retention period, access-control specifics, and any partner-specific consent terms are
**UNRESOLVED** and must be settled by the data owner before Stage B. This document does not invent
guarantees for them.
